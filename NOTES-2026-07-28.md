## 3. Bug #1 — `rec.log` spans multiple boots (fixed)

**Symptom:** collector connected and said `streaming`, but the entire 1 Hz
metric tier was silently empty. No errors anywhere.

**Cause:** `rec.sh` writes its `#beacon-rec` header *only if the file does not
exist* (`device/rec.sh:30`) and is append-only across reboots by design (§7).
So one `rec.log` holds several boots with no marker between them, and uptime is
monotonic only *within* a boot. `backfill_and_follow` deduped with a strictly
increasing `up > seen` rule. Replaying the old segment pinned `seen` at the
previous boot's max (9064.23), so every line of the new boot (302→805) failed
the test and was dropped **forever**.

The same root cause produced a second symptom: stale lines that *did* replay
were stamped `current_boot_epoch + old_uptime`, landing points **hours in the
future** (out to 21:04). Those future points then collided with live data —
interleaved sub-second inside the same series with identical labels, which is
why they could not be filtered out by any query, only waited out or deleted.
(VictoriaMetrics `delete_series` rejects `start`/`end`, so surgical deletion of
a time range is not possible — it is all-or-nothing per series.)

**Fix:** `recorder._current_boot_lines()` — split the dump at the *last* uptime
decrease and replay only the newest segment; plus end the stream on a
mid-follow uptime reset so the supervisor re-establishes `boot_epoch`.
3 regression tests in `test_parsers.py`.

## 4. Bug #2 — `logcat -T` argument splitting (fixed)

**Symptom:** after the nightly reboot, the collector spun in a ~6 s loop for
~90 minutes collecting nothing. Log signature, with **no ERROR lines**:

```
streaming (boot_epoch=…)
stream …-logcat ended cleanly (EOF)
session ended; will reconnect
```

**Cause:** `adb shell` joins its argv with spaces and the **device** shell
re-splits, so `-T "07-28 23:30:00.000"` arrived as `-T 07-28` plus a stray
`23:30:00.000`, and logcat exited immediately with `not in time format`.
Because the supervisor uses `asyncio.wait(FIRST_COMPLETED)`, that one EOF tore
down all six streams; every retry re-sent the same broken `-T`, so it could
never recover. Measured: unquoted → 1 line (the error); quoted → 9355 lines
streaming.

This is the *same* gotcha already documented in `recorder.ensure_running` for
compound commands — it had simply never been applied to `-T`.

**Why it stayed hidden since M0:** `-T` is only used on *reconnect*. The
session had run 3+ hours straight without one. The 22:00 MDM reboot triggered
the first reconnect the code had ever performed.

**Fix:** `streams.py` — wrap the value in quotes that survive to the device
shell (`f"'{since}'"`). 1 regression test in `test_pipeline.py`.

**Generalise this:** any `adb shell` argument containing a space needs the same
treatment. Worth auditing if new commands are added.

## 5. Findings about the device itself

### GPU pages are NOT leaking

This looked alarming and turned out to be benign — worth recording so it is not
re-litigated.

The panel showed the floor climbing +22.8 MiB in 38 min (≈ +30 MiB/h, which
would OOM a 3.66 GiB device in ~3 days). But the previous boot, re-mapped to
its own uptime, was **flat for 100 minutes**:

| uptime | floor | ceiling |
|---|---|---|
| 55m | 58721 | 81335 |
| 95m | 59308 | 80584 |
| 135m | 57615 | 86092 |
| 145m | 59682 | 81540 |

Both boots converge on the same **~59k plateau**. What we watched was the
warm-up ramp to a bounded working set, essentially complete by ~45 min uptime.

Mechanism: only **3 distinct creatives** cycling every **2.1 s** (565
switches/hour), so the working set was complete within seconds — nothing was
still loading. What grows is the **Mali driver's page pool**, which retains
freed pages for reuse and grows to the high-water mark of peak demand. Hence
ramp-then-plateau, and hence the ~30k-page (120 MiB) sawtooth in the raw trace.

**Thresholds** (`pages × 4096 = bytes`; device has 3.66 GiB total, ~2.2 GiB
available):

| | pages | MiB |
|---|---|---|
| normal floor | 55–61k | 216–238 |
| normal ceiling | 80–90k | 313–352 |
| watch | floor > 77k | 300 |
| bad | floor > 102k | 400 |
| critical | floor > 128k | 500 |

Per §1.4, **do not alert on the absolute value** — it false-fires constantly
against the sawtooth. Alert on the *floor* and its *slope*:

```promql
min_over_time(stick_gpu_pages{serial="…",proc="dplayer"}[30m]) > 76800     # sustained 2h+
delta(min_over_time(stick_gpu_pages{serial="…",proc="dplayer"}[30m])[4h:]) > 20000
```

### GPU faults correlate with app WebView context loss

The strongest real signal found. At **18:49:19.632**, same second:

```
[1015.471434] mali fe400000.bifrost: Failed to soft-reset GPU (timed out after 500 ms), now attempting a hard reset
[1015.471530] mali … t6xx: GPU fault 0x4002 from job slot 1
18:49:19.632  1710  E chromium: RasterDecoder context lost via ARB/EXT_robustness. Reset status = GL_UNKNOWN_CONTEXT_RESET_KHR
```

pid 1710 is `com.dolphin_us.dolphinstore`. Kernel resets the GPU → the app's
renderer loses its context. Bursty, roughly **one GPU reset every 10–20 min**,
each burst carrying exactly one `Reset_complete`. 60 GPU faults and 32
`JOB_READ_FAULT` in the observed window. The soft-reset times out and escalates
to a hard reset every time. Not every kernel fault reaches the app — only the
escalated resets do. This is the incident-engine case for M4.

Note the envelope steps do **not** track the fault times, so the faults are not
what drives GPU memory growth. Separate problems.

## 6. The on-device recorder earned its design

When the collector was stuck in the 90-minute reconnect loop, **no metric data
was lost**. `rec.sh` runs detached, writing 1 Hz to flash independently of adb
(§1.12); on reconnect, `backfill_and_follow` replayed the entire gap with the
correct `boot_epoch`. Verified: ~1090 samples/10 min straight through the
outage.

Text tiers were only partly recovered — Loki refuses entries older than ~45 min
(`entry too far behind`). Those lines are safe in Parquet but are not
queryable in Grafana for that window.

## 7. Dashboard changes

Loki indexes only **4** labels — `level`, `serial`, `service_name`, `source` —
so Grafana's ad-hoc filter cannot match on log *content*; that needs a LogQL
line filter. Added three template variables to `deploy/grafana/dashboards/device-detail.json`:

- **Log source** (multi) · **Level** (multi, this is the verbose toggle) ·
  **Text filter (regex)** (free text, defaults `.*`)

Logs panel is now:

```logql
{serial="$serial", source=~"$logsource", level=~"$loglevel"} |~ "$grep"
```

Useful filters: `mali fe400000` (anchor on this — bare `mali` also matches a
neighbour's WiFi SSID `…maliakal's iPhone`), `GPU fault|JOB_READ_FAULT|soft-reset`,
`context lost|Context reset`.

Provisioning has `allowUiUpdates: true` and a 30 s reload interval, so editing
the JSON on disk is picked up automatically.

**Annotation warning:** the `creative change` toggle fires 565×/hour and paints
every panel solid blue at a 1-hour range. Leave it off unless zoomed to minutes.

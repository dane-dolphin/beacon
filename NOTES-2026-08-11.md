Beacon now runs on **hyperion**, collecting seven devices on the office LAN.
This is the session where it left the dev laptop. `DEPLOY.md` is the runbook;

## Start here tomorrow

```bash
cd /opt/beacon && ./scripts/check.sh
```

Then the three things with a deadline, in order:

### 1. Did the spool prune fire? (disk — this one has a clock on it)

The 24 h grace expires around **22:47 on 08-12**, so the first automatic delete
happens shortly after. You wanted the first real delete supervised — see the
numbers *before* the collector acts:

```bash
cd /opt/beacon && .venv/bin/beacon prune --dry-run
grep "spool prune" var/beacon.log | tail -5
du -sh var/spool var/parquet
```

At 22:53 on 08-11 the spool was **529 MB after ~75 min** — about 420 MB/h
across 7 devices, or ~60 MB/h/device. That is **roughly double** plan.md's
28 MB/h/device estimate; either these devices are chattier than the D-005 bench
or the §3.4 denylist trims less on these platforms. Extrapolated, the standing
spool settles near 10 GB once the 24 h window fills, against 80 GB free — fine,
**if pruning works**. If `var/spool` climbs past ~15 GB with no prune lines,
the conversion-verify path is failing; get the WARNING lines.

Deletion additionally requires the Parquet object to exist with a matching row
count, so a mismatch keeps the file and logs rather than losing data.

## GPU freeze experiment — live as of 2026-08-11 23:00

Setup: one web creative plus a static JPEG per stick.

| stick | web creative | displays | page-fault sequences |
|---|---|---|---|
| `D-005-02408` | weather `azdd-PRODUCT-1778274790998` | 308 | **2** |
| `D-005-01860` | portrait `azdd-PRODUCT-1784673503560` | 202 | **0** |

Both creative IDs match the ones analysed on 07-29, so the comparison is clean.

**Both faults on 02408 recovered.** Full sequence at 22:13:34 and 22:18:45:

```
Unhandled Page fault in AS0 at VA 0x0  ->  slot 0 TERMINATED
JS: Job Hard-Stopped x2  ->  Preparing to soft-reset
Resetting GPU (allowing up to 500 ms)  ->  register dump
Failed to soft-reset GPU (timed out after 500 ms), now attempting a hard reset
Reset complete            <-- the line that was ABSENT on the 07-29 freeze
```

That final pair is the entire difference between benign and fatal. Neither
stick is in the dangerous state.

### Against the 07-29 baseline

Historical rates, both creatives on both sticks (computed from the full local
Parquet, 07-28..08-01):

```
D-005-02408  portrait  62/11050 = 0.561%     weather  5/11161 = 0.045%
D-005-01860  portrait  39/ 5491 = 0.710%     weather  1/ 5560 = 0.018%
```

Applied to the A/B:

```
02408 weather   observed 2 in 308 displays; predicted 0.14   P(>=2) = 0.0087
01860 portrait  observed 0 in 202 displays; predicted 1.43   P(0)   = 0.24
```

**Weather is faulting at ~14x its own historical rate — about the rate portrait
used to have.** That is the surprising number, and it runs against the 07-29
conclusion that portrait was 14–39x worse.

**Portrait's zero means nothing yet.** At 202 displays you would only expect
~1.4 faults, so zero is unremarkable. Do not read it as vindication.

### Caveat that may matter more than the numbers

Historically both WebViews held *web* creatives and ping-ponged; the fault
fired ~1.0 s into prefetching the next one. Now each stick alternates one web
creative with a **static JPEG**, so the prefetch pattern itself has changed. If
the mechanism needs a WebView-to-WebView swap, this setup cannot reproduce it,
and you are measuring something else. **A third stick running the original
weather-portrait pairing would be the control that settles it.**

### Statistical power

At ~200–300 displays/hour/stick: **~8 h** yields ~10 faults on a 0.6%-rate
creative (enough to confirm a high rate); **2–3 days** to say anything
confident about a 0.045% creative.

### What actually predicts a freeze

Nothing in the metric tier. The 07-29 freeze went normal-to-dead in <1.1 s with
GPU pages, memavail, temps and load all inside their normal bands. The only
signal is the dmesg pattern: **`Resetting GPU` with no `Reset complete`**.
That incident rule is M4 and is not built, so nothing alerts on it today.

If a stick does freeze: **do not cold power-cycle it.** ramoops is enabled and
a warm reset preserves `/sys/fs/pstore`; a power pull wipes it. Capture with
`scripts/freeze_forensics.sh <addr>`.

## Built today

- **`rec.sh` v2 — per-process CPU/RAM**, confirmed working on real hardware.
  A `#top` line every ~33 s carrying top-5 by RSS with PSS, utime/stime,
  MemTotal and CLK_TCK. The 1 Hz line is byte-identical to v1. Device reports
  `CLK_TCK=100`, `MemTotal=3991028 kB`.
- **Open LAN discovery** — sweeps the subnet, adopts unknown serials, relocates
  known ones that changed lease. Off by default.
- **Device console** — `beacon devices` and `beacon serve`, with
  name/app_package/skip overrides in `device_overrides`, re-read every
  supervisor cycle so edits need no restart.
- **`scripts/check.sh`** — read-only health check, exits non-zero on trouble.
- Unreachable devices now log; previously a 13 h outage was silent.

### Bugs found and fixed, worth remembering

- **Loki poison batch.** `batch_max` was set in `__init__` and never used, so
  `flush()` built one unbounded payload. Four devices produced 5.6 MB against
  Loki's 4 MiB gRPC limit; the failed batch requeued at the same size and
  retried forever. Payloads now split; oversized spooled ones re-split on
  drain; both Loki configs raise the gRPC and ingestion limits.
  **Loki reads config only at startup and a bind-mounted change does not alter
  the container spec — `docker compose up -d` reports "Running" and changes
  nothing. Use `docker restart beacon-loki`.**
- **Cardinality, caught on real data.** Real WebView renderers are named
  `com.google.android.webview:sandboxed_process0:org.chromium…Service0:0`.
  Collapsing digits only in the last colon segment left `process0`/`process1`
  distinct, and the 64-char cap truncated mid-token so they stayed distinct —
  one permanent series per renderer. Digits now collapse in every segment and
  segments past the second are dropped. **Not deployed until hyperion pulls.**
- **The console lied.** `touch_device()` existed and was never called, so
  `last_seen` held the connect time and every streaming device read "idle".
- **`_pump_applog` returning early** would have won `asyncio.wait(FIRST_COMPLETED)`
  and torn down every stream — the same failure mode as the 07-28 logcat bug.
  Gated at task creation instead, with a regression test.
